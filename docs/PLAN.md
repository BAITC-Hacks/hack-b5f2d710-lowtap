# План проекта «Аким на 5 часов» — команда lowtap

Спец-трек Astana Innovations. Полное условие: [TASK_SPEC.md](TASK_SPEC.md).

## 0. Главная идея (что мы продаём жюри)

**Детерминированный движок считает, AI-агент объясняет и советует, отдельная проверка ловит выдуманные числа.**

- Движок (engine) — единственный источник чисел: валидатор правил, расчёт Score, атрибуция вклада каждой меры, оптимизатор. Покрыт тестами на эталонных числах из условия.
- AI никогда не считает. Он получает готовый JSON с фактами и:
  1. **Аналитик** объясняет результат: сильные стороны, риски, последствия, компромиссы (structured output).
  2. **Советник** — агент с инструментами `simulate / validate / find_swaps / compare`. Предлагает улучшения, и каждое предложение сначала прогоняется через движок.
  3. **Ведущий событий** озвучивает кризис из фиксированной колоды событий (эффекты событий детерминированы).
- **Защита от галлюцинаций (grounding guard):** каждое число в тексте LLM сверяется с фактами движка. Если найдено «чужое» число, ответ перегенерируется или помечается. Требование «числа он не считает и не придумывает» так проверяется кодом.
- **Работает без API-ключа:** офлайн-режим строит объяснение по шаблонам из тех же фактов. Жюри сможет запустить проект без ключа, это прямые баллы за воспроизводимость.

Что из этого следует для продукта:
- Разброс Score узкий: 52–57. В UI нужно показывать **дельту к базе и перцентиль** («ваш план лучше 87% из 694 395 возможных»), а не только само число.
- Полный перебор реален, поэтому оптимизатор точный, не эвристика. Считаем один раз при сборке, храним отсортированные результаты.
- «Ловушки» (планы хуже бездействия) хорошо смотрятся в демо: тратишь деньги и делаешь хуже. Это показывает, что модель не игрушечная.

## 2. Архитектура

```
┌──────────────── web (React + Vite + TS) ────────────────┐
│ Брифинг → Комната решений → Итоги → Советник → Кризис → │
│ Лидерборд → Экспорт презентации                          │
└───────────────────────────┬──────────────────────────────┘
                            │ REST + SSE (стриминг объяснений)
┌───────────────────────────▼──────────────────────────────┐
│ api (FastAPI)                                            │
│  ├─ engine/  (чистый Python, без зависимостей от AI)     │
│  │   data · validate · simulate · attribution(Shapley)   │
│  │   optimizer · stress-test · percentile                │
│  ├─ ai/                                                  │
│  │   analyst · advisor-agent(tools→engine) · events      │
│  │   grounding_guard · offline_templates                 │
│  └─ store/ SQLite (лидерборд, сохранённые сценарии)      │
└───────────────────────────┬──────────────────────────────┘
                            │ OpenAI API (Responses API + Agents SDK)
                            │ или любой OpenAI-совместимый сервер (OPENAI_BASE_URL)
```

**Стек:** Python 3.12 + FastAPI + pytest · React + Vite + TypeScript + Tailwind + shadcn/ui + ECharts (или Recharts) + Framer Motion · SQLite · Docker Compose · OpenAI Python SDK + OpenAI Agents SDK (`openai-agents`).

**LLM-слой (OpenAI):**
- Аналитик — один вызов Responses API со Structured Outputs (ответ строго по JSON-схеме: `strengths / risks / consequences / tradeoffs`).
- Советник — `Agent` из Agents SDK, инструменты движка через `@function_tool`, а grounding guard подключён как `output_guardrail`. Трейсы агента видны в дашборде OpenAI, их удобно показывать жюри.
- Настройки в `.env`: `OPENAI_API_KEY`, `OPENAI_MODEL` (по умолчанию `gpt-6-sol`), `OPENAI_MODEL_FAST` (`gpt-6-luna` для коротких текстов: новости событий, «голоса районов»), `OPENAI_BASE_URL` (необязательно). Какие модели доступны вашему ключу, проверяется через `GET /v1/models`.
- Весь LLM-код лежит в `backend/ai/llm.py`. Провайдер меняется в одном месте, движок от него не зависит.
- Без ключа включается офлайн-режим (шаблоны). С `OPENAI_BASE_URL` можно подключить локальную модель (Ollama или LM Studio).

Почему не всё на TS: движок и тесты на Python пишутся быстрее всего, а один сервер означает одну формулу (без дублирования в браузере). Движок отвечает за миллисекунды, поэтому ощущение «сразу видно последствия» сохраняется.

**Структура репозитория:**
```
data/scenario_v1.json      # бюджет, районы, меры, синергии, конфликты, веса (+ SHA-256 в UI)
data/events_v1.json        # колода городских событий (детерминированные эффекты)
backend/engine/            # validate.py simulate.py attribution.py optimizer.py
backend/ai/                # analyst.py advisor.py events.py guard.py prompts/
backend/api/               # main.py routes
backend/tests/             # эталонные числа + каждое правило валидатора
web/                       # фронтенд
examples/                  # plan_spec_example.json, plan_cheapest.json, plan_invalid_*.json
docker-compose.yml  Makefile  .env.example  README.md
```

**API-контракт (фиксируем первым, чтобы фронт и бэк шли параллельно):**
| Метод | Что делает |
|---|---|
| `GET /api/scenario` | бюджет, районы, меры, правила, хеш сценария |
| `POST /api/validate` | `{plan}` → `{valid, errors:[{code, message, measure}]}` |
| `POST /api/simulate` | `{plan}` → Score, D_avg, D_d, N_crit, значения до и после, вклад мер (Shapley), перцентиль |
| `POST /api/explain` (SSE) | стриминг объяснения аналитика, результат проверен guard'ом |
| `POST /api/advise` | агент-советник → список проверенных улучшений с Δ |
| `POST /api/compare` | 2+ плана → таблица различий + AI-комментарий |
| `GET/POST /api/leaderboard` | результаты команд (одинаковый хеш сценария) |
| `POST /api/event` | выдать событие (seed) → новый бюджет или эффект, нужно перераспределить |
| `POST /api/presentation` | 5 слайдов HTML/PDF по итогам |

## 4. Экраны (визуал — отдельный приоритет)

1. **Брифинг акима.** Стилизованная карта Астаны (5 районов, цвет по D_d), профили районов, базовый Score 52.56, бюджет 100, «часы» 8 кварталов.
2. **Комната решений.** 5 слотов-карточек. Каталог 14 мер по направлениям. Район выбирается кликом по карте. Шкала бюджета заполняется. Лимит «≤2 на направление» и конфликты видны сразу. Живой превью-Score.
3. **Итоги.** Крупный Score с анимацией счётчика, Δ и перцентиль, waterfall «база → вклад мер → итог», heatmap до/после, радар района, перекраска карты, таймлайн лагов (с какого квартала мера начинает работать). Справа стримится AI-разбор.
4. **Советник.** 2–3 проверенных предложения («заменить M11 на M9 в Нуре: +0.8») с кнопкой «Применить».
5. **Кризис.** Новость о событии (текст пишет LLM, эффект задан в данных) → перераспределение.
6. **Лидерборд / сравнение** и **экспорт презентации**.

Дизайн: тёмная тема «ситуационный центр», акцент бирюзовый и золото (цвета флага), крупная типографика цифр, плавные переходы. Референс — городские дашборды, не «админка».

## 5. Этапы работ

Дедлайн и размер команды пока неизвестны, поэтому этапы идут по порядку, с **точками остановки**: после каждой точки проект уже можно сдавать.

### Этап 0. Старт (≈1 час, делает один человек, остальные читают условие)
1. Настроить git-идентичность (сейчас не задана):
   ```bash
   git config user.name "Имя Фамилия"
   git config user.email "you@example.com"
   ```
2. Bootstrap-коммит **прямо в `main`** (репозиторий пустой, конфликтов не будет): `docs/`, `.gitignore`, `.env.example`, структура папок, `data/scenario_v1.json`, заготовка README, `docker-compose.yml`-скелет.
3. Зафиксировать API-контракт (раздел 2) и JSON-формат плана:
   `{"decisions":[{"measure":"M7","district":"Нура"}, {"measure":"M12"}]}`
4. Распределить роли (раздел 6). **С этого момента в `main` только через ветки и PR.**

### Этап 1. Движок + тесты (критический путь)
- Ветка `feat/engine`: загрузка данных → валидатор (коды ошибок: `BUDGET_EXCEEDED`, `NOT_FIVE`, `DUPLICATE`, `DISTRICT_REQUIRED`, `DISTRICT_FORBIDDEN`, `DIRECTION_LIMIT`, `INCOMPATIBLE_M1_M3`, `CONFLICT_M4_M7`, `CONFLICT_M5_M13`) → simulate → Shapley → оптимизатор с кешем.
- Тесты: 52.558 / 56.543 / 55.667, по тесту на каждое правило, 694 395 валидных планов, максимум 57.237.
- CLI: `python -m engine score examples/plan_spec_example.json`.
- Параллельно `feat/web-ui` делает интерфейс на моках по контракту.

### Этап 2. API + MVP-интерфейс → 🟢 ТОЧКА ОСТАНОВКИ 1 (все MUST)
- `feat/api`: эндпоинты scenario/validate/simulate/explain (пока офлайн-шаблоны).
- Фронт подключается к API: выбор мер, бюджет, Score, объяснение.
- `docker compose up` поднимает всё. Первый вариант README с запуском.

### Этап 3. Настоящий AI → 🟢 ТОЧКА ОСТАНОВКИ 2
- `feat/ai`: аналитик (structured output: strengths / risks / consequences / tradeoffs), grounding guard, стриминг по SSE.
- Агент-советник (OpenAI Agents SDK: инструменты вызывают движок, guard висит как output guardrail), предложения с проверенной Δ.
- Сохранить 3–5 эталонных ответов как регрессионные примеры.

### Этап 4. Вау-визуал
- Карта районов, waterfall, heatmap, анимации, таймлайн лагов, перцентиль.

### Этап 5. Опциональные фичи (по времени, в порядке ценности)
- Стресс-тест лагов → события → лидерборд/сравнение → презентация → «голоса районов».

### Этап 6. Упаковка (**последние 15–20% времени, не сдвигать**)
- README (раздел 7), скриншоты и GIF, `make test` зелёный, чистый `git clone` → `docker compose up` на другой машине.
- **Code freeze** за 1–2 часа до дедлайна, только фиксы.
- Желательно поднять публичное демо (VPS, Render или Railway). Ключ OpenAI хранится только на сервере, на запросы стоит лимит. Ссылку на демо положить в README: жюри сможет попробовать с AI, не имея своего ключа.
- Репетиция демо на 3 минуты: базовый город → «наивный» план (ловушка хуже бездействия) → разбор AI → совет агента → +Δ → кризис → лидерборд.

## 7. Git-процесс

- `main` всегда запускается. Ветки живут коротко (часы, не дни): `feat/…`, `fix/…`, `docs/…`.
- PR через веб-интерфейс GitHub (`gh` не установлен), squash-merge, один человек смотрит PR.
- Сообщения коммитов в стиле Conventional Commits: `feat(engine): shapley attribution`.
- Перед PR: `git pull --rebase origin main`, `make test`.
- Секреты только в `.env` (в `.gitignore`), в репозитории лежит `.env.example`.
